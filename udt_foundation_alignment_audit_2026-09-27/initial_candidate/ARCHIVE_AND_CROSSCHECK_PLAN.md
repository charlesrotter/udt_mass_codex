## Practical sequence for archiving

The default is to archive after the audit/distillation stages establish what must
remain easy to retrieve. Physical relocation need not wait indefinitely for the
physics to succeed: once classification and retrieval gates pass, it can be its
own bounded maintenance task. During research, narrow the startup reading path
immediately through existing current surfaces and task-specific source pointers.

Classify a proposed archive inventory by role:

1. Current authority and maintained navigation: stay readily visible.
2. Controlling evidence, negative results, failure records and provenance needed
   by active claims: remain reachable through stable registry/source references.
3. Superseded status narratives and completed working notes: archive candidates,
   provided every live dependency has a durable route.
4. Protected, unrelated, untracked, externally stored or fixed-path historical
   records: excluded unless a separate explicit dispatch permits the exact action.

This is a proposed classification, not a claim that all 33,248 tracked files have
been classified. The 406-row registry is not a complete dependency graph. Plain
text links also miss dynamically constructed paths and external references.

Before any move, save a source commit, exact source/destination manifest, SHA-256
pins, reverse references, replacement navigation and restoration instructions.
Retain original filenames where possible and byte-identical historical bodies.
Never rewrite old readiness/ownership snapshots to masquerade as current reports.
Never delete failed or superseded science simply because it distracts.

Do not move the three fixed-path root rehearsal artifacts or treat the ignored
memory export as current authority. Query the existing relocation ledger only for
known old paths; do not convert it into a second current-frontier index. Extend
the established relocation mechanism only after inspecting its actual consumers
in the later maintenance task. Protected local payloads remain untouched.

Use a small proposed first batch, not a mass move. Rehearse the relocation in an
isolated checkout under a later written work order. Check both file contents and
the code/docs that consume paths, required premise checks and restoration. Have
a fresh reader recover: a current result, its contrary control, an old original
prompt, a superseded claim and the reason it was superseded. Require exact source
recovery and correct authority/grade, not just a shorter directory listing.
Only then integrate the reviewed batch. Git preserves rollback; it does not by
itself guarantee that a new session will find the right evidence.
