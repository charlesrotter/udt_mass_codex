# G298 lay report

The metric gives us more than we were trying to squeeze into one pair plane.

For any chosen light route, it tells us how the source clock compares with the target clock, which
way the light leaves the source, which way it arrives at the target, and how the source's local
frame is carried along the route. That is a coherent, native relation state.

But there are at least two natural regular projections of that richer state into the two directions
used by the local pair evaluator:

1. use the target clock plus the source's ruler direction carried to the target;
2. use the target clock plus the target's own local light direction.

When there is no sideways or angular mismatch, those choices describe the same plane. When the
screen sector is active, they are genuinely different planes. Both still give the same direct
reciprocal redshift. The target-local `J_L` view is a **natural regular projection that forgets
transported-source/path carry**; it is not a second equally complete physical relation. So the
redshift part is solid, while the rule for reducing the complete relation to one pair plane is not
unique yet.

This is useful narrowing. We are no longer missing an unspecified “history” at this local step. We
have found the exact remaining choice: either identify which projection is physical, or let the
kernel's physical input be the richer route-labelled relation and treat each pair plane as a query
view of it.
